Open Commerce — internal reference

Who lands where, and what happens next

Three kinds of people use this today: a seller listing a component for sale, a shopper's AI assistant buying one, and a developer connecting their own AI tool to the system. Each one moves through a different set of pages, hosted on three different services, with real money changing hands along the way. This shows what actually works right now — not what's planned.

What this map shows

  • Nobody can find the landing page on their own. It's fully built and live, but nothing else in the project links to it — the only way to visit it is if someone hands you the link directly.
  • People can't buy anything themselves yet. If a person visits a storefront page, they see the same information an AI agent would, but there's no working "buy" button for them — only AI agents can actually complete a purchase right now.
  • There's a real submission page for sellers now, but it's not actually online. It runs on a developer's own computer (localhost:3002), with real safety checks and validation. Hosting for it is planned — a Render service is declared for it — but that hosting has never actually been turned on (we checked: it doesn't exist live), so no real seller can reach it yet.
  • Sellers can now have their own separate accounts, but only one ever has. Signing up, logging in, and keeping each seller's data separate all genuinely work — but the only account that exists is Priya's, and it was moved into the new system rather than created by going through the actual signup form. Nobody's proven the whole thing works end-to-end for a brand-new seller yet.
  • There are two separate ways for an agent to find a component, and neither depends on the other. The registry (using MCP) and the information embedded directly on the web page both work on their own — an agent doesn't need to know the registry exists if it can just read the page.
  • There's no refund or dispute handling. A completed sale has no way to reverse it — no refund endpoint, no chargeback handling — beyond whatever a seller does manually in their own Stripe dashboard.
  • Buyer payment setup is built but not yet verified end-to-end. POST /api/buyer/setup now mints a buyer_token and a real Stripe Checkout Session for the buyer to complete; on return, the payment method gets registered automatically. Every part except the actual browser click-through has been tested — nobody's completed a live session yet.
